# A search corrects the object it can reach, not the one the claim is about

**Applies** the moment you CORRECT a claim about an artifact by searching for it —
a grep, a catalogue read, a file scan. The correction is trusted more than the
original (it is dated and deliberate), so a wrong one is worse than the fault it
"fixes".

**The rule.** Name the OBJECT the claim is about, and confirm your instrument can
REACH that object, before you overwrite the claim. A repo grep reaches only what is
in the tree; an artifact produced by code that lives OUTSIDE the tree is invisible
to it, and a same-shaped object the grep DOES find is a WRONG-OBJECT correction that
carries the authority of a fresh reading. Where the real object is out of reach,
DERIVE its value from the evidence that names it, or say "not measurable from the
tree" — never substitute what the tree happens to hold.

## The instance — two objects of one shape, and the correction took the wrong one

`PROJECT_STATUS.md`'s commit-3 record claimed the PromptPay samples were "generated
from HIS PromptPay number, supplied at the STOP" — an intention written as an
observation (the failure this project pays for most often), and it did need
correcting. The correction (2026-09-12) grepped the tree for the sample's proxy,
found `0812345678` at `mobile/src/proof/provePromptPay.ts:147`, and wrote that the
brief's "placeholder `0000000000`" was "inexact" and "the owner's number is not
here". **Every clause of the fix was about the wrong object.**

- The SAMPLES were generated by `gen_samples.mjs`, which lives OUTSIDE the
  repository tree BY DESIGN. A repo grep cannot see it and returns ONLY the proof's
  fixture — a different object of the same shape.
- The correct value, `0000000000`, was derivable all along by parsing the sample
  payload quoted in commit 3's own STOP report: its tag-29 sub-01 proxy is
  `0066000000000` = `0066` + national number `000000000` = mobile `0000000000`. The
  PROOF fixture's proxy is `0066812345678` = `0812345678` — the SECOND object.
- So the brief's `0000000000` was RIGHT; the grep-based correction conflated the
  generator's sample with the proof's fixture and dismissed the true value.

## Why it is costly, and why nothing caught it in-session

A correction inherits more trust than the sentence it replaces. Converting a
true-but-mislabelled fact (an intention-as-observation) into a confident falsehood
is a net loss: the reader now believes a wrong thing stated deliberately. Nothing
in the tree could catch it, because the disproving object (the sample payload with
`0066000000000`) exists only in the STOP report, not in any file a check opens. It
was caught only because a reader held BOTH objects — the sample payload AND the
fixture — from that report. A reader without both cannot.

## How to apply

1. **Before correcting a claim, name the object it is about and ask whether your
   instrument can reach it.** A grep reaches the tree only. If the object is
   generated, fetched, or rendered by something outside the tree, the grep is
   answering a neighbouring question, not the one you asked.
2. **When the object is out of reach, derive from the evidence that names it** (a
   quoted payload, a log line, a stored value) rather than substituting the nearest
   same-shaped thing the tree does hold. Or state "not measurable from the tree".
3. **A correction is a claim; hold it to the higher bar, not the lower one.** The
   original may be sloppy; the fix must be measured, or it is a worse sentence than
   the one it replaced.
