# Lessons

Hard-won rules that would cause a real bug if forgotten. One file per lesson.
Read these at the start of a session; add/update one before finishing a phase
whenever a real mistake was made and fixed, or a non-obvious constraint was
found. Not for general tips — only for things that bite.

- set-local-per-request.md — applies whenever code sets tenant/RLS context: use SET LOCAL inside the request transaction, never session SET; unset = no context (fail closed), never all-tenants.
- revoke-in-migration.md — applies to any privilege GRANT/REVOKE or DB permission change: put it in the migration, never run it live once.
- login-resolves-under-tenant.md — applies to auth/login and any per-tenant identity lookup: resolve the user inside tenant context; return one generic error for both unknown-user and bad-password.
- schema-audit.md — applies before committing any migration: read it field-by-field against the agreed schema; green proofs do not prove the schema is right.
- sync-state-needs-startup-recovery.md — applies to any "in progress" state (syncing, claimed, locked): nothing polls it, so a crash strands the record forever unless startup sweeps it back to retryable.
- unavailable-is-not-rejected.md — applies to every sync/retry path. THREE-WAY, not two: unknown outcome (offline, timeout, lost response) retries forever; a PERMANENT refusal (422, malformed) goes terminally failed; a RESOLVABLE refusal (424, master data not set up) parks — still owed, out of the sendable queue, retried when the data is fixed. The question is not "did it fail" but "can anything make this bill valid later, and does the failure NAME what". Marking resolvable as permanent strands a load already tipped into the pile.
- sqlite-money-is-text.md — applies to any money/weight stored in SQLite: NUMERIC affinity silently converts decimal strings to floats and STRICT does not protect TEXT columns; the guarantee is the TypeScript type, not the DB.
- sqlite-busy-timeout-first.md — applies to every SQLite connection: PRAGMA busy_timeout must precede all other statements, including journal_mode, or setup itself throws "database is locked" intermittently.
- concurrency-tests-need-a-barrier.md — applies to any test asserting behaviour under concurrency: without a start barrier and printed overlap evidence, the workers ran sequentially and a green result proves nothing.
- metro-file-map-nesting.md — applies when a bundler/resolver claims a file is missing that exists on disk: ask its index, not the OS. Never nest npm packages; keep a run ledger, because one green run pinned the wrong cause.
- a-proof-fixture-must-be-a-row-the-product-could-produce.md — applies to every proof/seed/test that writes business rows directly instead of through the real path. IF `POST /bills` COULD NOT HAVE PRODUCED THE ROW, IT IS NOT A FIXTURE. The reconciler's first run was red with 84 violations, none of them product defects: `prove_rls` INSERTs a bill with no doc_no (it needs a direct INSERT to exercise the RLS WITH CHECK — but that requirement is about the INSERT, not about leaving doc_no empty), and `prove_daily_report` backdates server_received_at away from the year its doc_no was already given. Both rows are schema-VALID and product-IMPOSSIBLE. Three harms, and the pollution is the least: an assertion over a hand-built row exercises the row and not the code that would have built it; and debris ARGUES FOR ITS OWN LEGITIMACY — the natural reading of a red check is "the invariant is too strict", after which the check can no longer see the real failure. Ways out, in order: go through the real path; write the WHOLE row including what the product would have filled; or make the fixture disposable and dispose of it (a throwaway tenant a proof invented is not what hard rule 5 protects). Never: teach the checker to tolerate it. The write-side twin of proof-must-run-twice — that one asks whether the GREEN means anything, this one whether the FIXTURE does.
- a-checker-must-not-share-the-code-it-checks.md — applies to every reconciler/audit/invariant check, and to every test that breaks something on purpose. TWO BOUNDS, opposite directions. DUPLICATE ARITHMETIC (the checker computes `round(net*price,2)` in Postgres NUMERIC so it can DISAGREE with the Decimal in `_line_amount`; importing that helper would only prove the code equals itself) but NEVER DUPLICATE A CONVENTION (`_be_year` is imported — a second `+543` is correct-by-luck all day and wrong across Bangkok midnight, which is the very amendment be-year-comes-after-the-timezone already carries). Test: could a second author, given only the spec, reach the same answer? Yes → duplicate; no → import. And a destructive proof must not reach past its copy: ROLES ARE CLUSTER-WIDE, so `ALTER ROLE recycle_app BYPASSRLS` — the only way to make the S5 role check fire — would disable tenant isolation on LIVE money data, while `ALTER TABLE ... DISABLE ROW LEVEL SECURITY` one line above it is database-scoped and safe; that check is left unproven-by-execution and labelled, with the refusal enforced by a scan rather than a comment. Every injection asserts three things: it fires, it NAMES the row, and it CLEARS when undone.
- proof-must-run-twice.md — applies to every proof script: it must pass twice in a row against a live DB with no truncate between. Hardcoded idempotency keys and absolute doc_no assertions proved the environment, not the code. AMENDED: the seed's SIZE is an environment fact too — `len(sellers) == 1` measured the fixture, not tenant isolation, and adding a seller broke it; assert the set relation. AMENDED AGAIN (0004): unique ≠ removable — a fixture the proof writes a BILL against can never be deleted (hard rule 5), so it pins itself forever; borrow a SEEDED row for those cases. Isolate every statement in `finally`, or one FK error skips the restores after it and replaces the summary with a traceback. And fix the whole CLASS of an assertion, not the line that went red — `len(products) == 3` survived the sellers amendment and bit later. AMENDED A FOURTH TIME: the other half — a second run that PASSES for the wrong reason. A proof that NORMALISES its own fixture as setup measures its previous run (`DELETE 0, UPDATE 0` under a green tick), so it must CREATE the fixture (call `restore_db.py` itself) rather than find it, and must SKIP rather than pass when a claim's precondition is absent.
- decimal-precision-for-domain-scale.md — applies wherever a decimal library does money math: its precision is per-operation and finite. NUMERIC(14,3) x NUMERIC(14,2) needs 28 significant digits; decimal.js defaults to 20 and silently zeroes the rest.
- wait-for-the-event-not-the-ticks.md — applies to any test that waits before observing: a fixed tick count bakes in the scheduler's shape and silently moves what moment you measure. Wait for the event, bounded, and print the cost.
- console-is-not-the-observation.md — applies before ever concluding "the data is corrupt": this box is codepage 874, so UTF-8 through a console or an unpinned pipe reads as mojibake. Verify with hex/codepoints at the source; the destructive fix is the phantom one.
- doc-no-is-arrival-order-not-event-time.md — applies to doc_no and to every report: doc_no is arrival order, so the send queue needs strict head-of-line ordering (a sort cannot order a row the backoff filter hides). Device clocks measured ~3s wrong, so aggregate on server_received_at, never device_created_at. BOUND: ordering holds within the SENDABLE queue only — a bill parked on missing master data is exempt and takes a higher doc_no; that is the one exception and it must not generalise.
- queue-jam-must-be-visible.md — applies to any strict in-order queue with no-give-up retry: a deterministically failing item (5xx = unavailable, not rejected) retries forever and dams everything behind it silently. Don't skip the head (that breaks ordering silently); make the jam visible, and tell an offline backlog (stay amber) from a poisoned head (go red) by whether the SERVER ANSWERED — not by elapsed time, which cannot separate a long outage from a poison pill. AMENDED: a consecutive-refusal COUNT may escalate an already-poisoned head, but must never classify one, and only because that counter resets on any transport-level bounce.
- render-in-shop-time-not-device-time.md — applies to every timestamp a human reads and every date derived for business meaning: store UTC, render via ONE formatter in the SHOP's timezone (never the device's, never a slice of the ISO string — that prints UTC verbatim, which showed 15:16 Bangkok as 08:16). UTC-derived dates also broke doc_no's BE year across new year, and the counter is keyed on it. zoneinfo has no IANA db on Windows; Hermes Intl timeZone is unverified. AMENDED (2d): the WIRE's precision is not the language's parse contract — Postgres timestamptz gives SIX fractional digits and the ECMAScript date format specifies exactly three, so the first server-produced instant ever rendered depended on an implementation-defined extension (V8 fine, Hermes unverified). Trim before parsing, truncate never round. Every instant rendered before it came from the device's own toISOString, i.e. the client had been defining its own input contract.
- config-defaults-must-fail-closed.md — applies to every secret/credential read from the environment: a default value is a default IDENTITY, and a forged token was accepted because of one. No default, empty counts as missing, and know that load_dotenv resolves .env from the CALLING FILE, not the cwd.
- edge-must-reject-what-the-column-rounds.md — applies to every money/weight field on a request model: NUMERIC silently ROUNDS an over-scale value instead of refusing it, and the resulting CHECK violation is a 500 = unavailable = a permanently jammed device queue. Declare max_digits/decimal_places/ge so it becomes a terminal 422.
- diagnosis-must-precede-the-fix.md — applies the moment a failure gets a cause: read the REAL traceback and the REAL files (does migration 0005 even exist?) before naming it, and run the disproof first. An explanation that fits a fear you already hold is the easiest to believe and least checked. The inverse of the "passing result is not evidence" family — a failing result pinned on the wrong cause.
- fallback-default-is-a-wrong-number.md — applies to every field that DEFAULTS from reference data: if the invented value cannot make the operation succeed, it is not a convenience, it is a wrong number the user acts on. A grade-less seller was quoted the grade-A (highest) tier on a bill the server refuses anyway — and the yard pays cash against the screen. Fail BLANK and say why.
- be-year-comes-after-the-timezone.md — applies to every พ.ศ. year rendered or derived: convert to shop time FIRST, then +543 — the other order is correct-by-luck for most of the day and wrong across Bangkok midnight, so it can only be proven at the boundary WITH the wrong order's output shown. One year source, branded shut so a raw instant will not compile. DD/MM/BBBB, never ISO-shaped 2569-07-26 (it invites being parsed as Gregorian). BOUND: the card's date and its doc_no year legitimately disagree for a bill that syncs across new year — created_at is weighing time, be_year is arrival time; do not "fix" that. AMENDED: the rule was applied to production and the PROOFS were never swept — the same expression survived in three places in two proof scripts for eight months and would have gone red on 2027-01-01 for seven hours with nobody having touched anything. When a lesson fixes a computation, the sweep is not done until every OTHER site of it has been checked, TESTS INCLUDED: test code is written to be independent of the implementation, which is exactly what makes it re-derive what the implementation now owns. Grep for the EXPRESSION, not the symptom. AMENDED AGAIN (2026-08-02): the derivation can be perfectly right and the ARGUMENT wrong — `_be_year(datetime.now(utc))` beside a `server_received_at` defaulting to Postgres' transaction-start `now()` is TWO CLOCKS AND TWO MOMENTS, a master-data round-trip apart, and a straddling submit took next year's be_year on last year's stamp. Not a mislabel: doc_no_counters is keyed on be_year, so it opened the wrong counter a year early and the new year's real first bill becomes seq 2 with no seq 1 — an unrepairable gap. A DERIVED VALUE MUST COME FROM THE TIMESTAMP THAT IS ACTUALLY STORED, read once and used for both; and the fix is an ORDERING, never a tolerance, because slack between two reads still leaves two reads.
- cached-master-data-is-a-price-claim.md — applies to any value DEFAULTED from cached reference data, and to every age computed from a stored timestamp. The server stamps list_price from the CURRENT list, so a bill priced off a stale cache is shaped exactly like a staff override. Past 12h the app must not default a price (show the cached number beside the empty box; block nothing else). The age is bounded by the OLDER of the two caches, but the clock-sanity check must read the NEWER — a future timestamp means the clock moved BACK, which understates every age and makes old data look fresh; min() hid that whenever only one list was affected. A delete-all refresh is one transaction, timestamp included, or half a list wears a fresh stamp. Stamp provenance at the START of the bill, never at the save.
- a-stored-future-instant-is-a-promise-about-a-clock.md — applies to anything scheduled from a device clock and every age derived from a stored device stamp: a stamp outside the window its WRITER could have produced is evidence the clock moved, not data. Backoff has a maximum, so a next_attempt_at past it is a clock reading — a 14h-fast phone corrected backwards stranded the whole head-of-line queue for 14h while the server answered. One rule, two bounds (a past stamp cannot be in the future; a schedule cannot exceed the horizon), OPPOSITE reactions: prices fail closed, the queue fails open. Check at READ time. Capping a reported duration does NOT disarm a trigger that reads it — keep "what we report" apart from "what we treat as evidence". A forward jump is undetectable from one stamp, so bound durations by the WORK that accounts for them, and attribute an age to the device clock rather than asserting it.
- 401-is-about-the-caller-not-the-bill.md — applies to every authenticated sync path: a 401 is neither unavailable nor rejected. The request was well-formed and the server answered — the CALLER is no longer anyone. Classify by WHAT THE FAILURE IS ABOUT (payload / network / server state / identity) before picking a class; the three classes of unavailable-is-not-rejected are all about the bill, so all three answer it wrongly. It must not feed the poison alarm (that counter means "the server refuses THIS bill", and a 401 refuses every bill), session state is device-global and derived, never stamped on a row, and the message must carry the sign-in button — the login screen renders on token === null, which is exactly false when a token EXPIRED.
- a-backup-is-a-claim-until-it-is-restored.md — applies to every dump/restore path and anything judged by an exit code rather than by inspecting what it produced. FORCE RLS means a dump by an RLS-bound role captures ZERO rows, and `--enable-row-security` "fixes" that error into a GREEN EMPTY BACKUP — so count rows in the DUMP FILE, never from the database. `--create` writes `\connect <db>` into the body, and that meta-command beats `-d`, so a "restore into scratch" silently overwrites production; take the body without it and re-check. `pg_dumpall` always emits a failing `CREATE ROLE postgres`, so the roles step cannot use its exit code — verify the END STATE, because a restored `recycle_app` with BYPASSRLS reads every tenant while the policies still look correct. And "restored matches source" is VACUOUS unless the source moved after the dump: mutate it, then require the restore to show the dump's moment (marker absent, doc_no counter one lower).
- a-defaulted-getattr-is-a-silent-dead-branch.md — applies to any attribute read off a foreign object (an exception, a driver) and to every safety branch no test is known to ENTER: `getattr(x, name, default)` cannot fail, so an ABSENT attribute reads as a confident negative and the branch it guards never runs. `e.orig.constraint_name` does not exist — SQLAlchemy's asyncpg dialect wraps the error and chains the real one as `__cause__` — so bills.py's idempotency-race handler was dead from Phase 1c and the loser of a same-key race got a 500 (= unavailable = a jammed device queue) instead of the winner's bill. Hard rule 4 held sequentially and failed under concurrency. Prefer asking the authority (re-SELECT the key) over recognising the symptom; where the name is genuinely needed, read it through one documented helper. The passing-result twin of diagnosis-must-precede-the-fix.
- 403-is-about-what-the-caller-may-do.md — applies to every authenticated path and every screen drawn by more than one renderer. Sibling of the 401 lesson: a 403 is also about the CALLER, but the caller IS someone and no tap on this device ever fixes it, so it is a FOURTH class and never a session variant (App clears sessionEnded on any server answer, so the refusal would evaporate every pass). Never "sign in", never "call support" — name the shop OWNER, not the office, who cannot change a role. THE DEFECT IT SHIPPED: one card, two renderers — voidProgressLine promised "จะดำเนินการให้อัตโนมัติ" two lines above a notice box saying the system had NOT cancelled it, both internally correct, both separately asserted, 448 green cells that could not see it. Assert the CONCATENATION in draw order; a screen assembled from independently-correct parts is not an asserted screen. And the two paths failed DIFFERENTLY — the void path never touched the poison counter (no `reachable` on VoidOutcome), it re-POSTed every 4s behind a false promise; the red alarm was the send path only. Reproduce a named mechanism, never just its conclusion.
- a-report-is-many-reads-that-must-agree.md — applies to any response assembled from more than one SELECT whose parts a reader will COMPARE: READ COMMITTED takes a FRESH snapshot per statement, so a bill committing mid-request is in the total and not in the list printed under it — an unreconcilable answer on the one screen whose job is reconciling, in a window too narrow to ever reproduce. Use REPEATABLE READ; a READ-ONLY repeatable read cannot raise 40001, but SERIALIZABLE CAN abort a read-only transaction, so never reach for "the strongest" on a report. Isolation is chosen at transaction START (before begin(), outside the SET LOCAL), and a level set late is silently ignored — assert `SHOW transaction_isolation` in BOTH directions or you have only proven a string came back.
- correct-classification-can-still-render-as-an-error.md — applies to every internally-distinguished state a user can see: server 424, transport, engine, SQLite, queue and proofs were ALL correct, and the screen still said ผิดพลาด in red with the raw JSON body and a seller UUID. A developer diagnostic (last_error) and an operator message are different artifacts; never render the former. A message naming an action must be DERIVED from the cause — hardcoded price wording told a grade-less seller to set a price, and a wrong instruction is worse than a vague one because the office acts on it. Assert NEGATIVELY on rendered text; every proof was green because none asserted on what the operator sees. Also: enumerate TRANSITIONAL states — a retry window leaked the same JSON back because releasing a state kept its error text, and a view-level gate is a bug you have not found yet. AMENDED (2c-7): that fix covered the state that bit and left its neighbours — offline cards still rendered the raw transport string in red, and a failed bill promised an automatic cancel that could never run. Fix the CLASS: enumerate the full cross product (proveNotice), remove the diagnostic from the parameter list rather than gating on it, never promise what the system cannot perform, and remember that narrowing does not survive a closure. AMENDED AGAIN (2d): a server `code` names the RULE THAT REFUSED, not the ACTION refused — one `require_admin` answers `admin_required` for every admin path, so wording hardcoded to the only caller told an owner opening a REPORT that a bill had not been cancelled. Wording is a function of (code, call site); make the call site a REQUIRED argument so the next screen is a compile error, never an optional one with the old sentence as its default. And a banned-substring list is context-dependent: `รวม 500 ใบ` is not a leaked 5xx — a regex over the class beats an enumeration of the statuses somebody remembered. AMENDED AGAIN (R2b): A WAIT IS A PROMISE ABOUT THE FUTURE, exactly as much as an offered action — "never promise what the system cannot perform" was written about a button and reads as being about buttons, but `รอให้ส่งครบก่อน` names a condition that cannot arrive when the queue is jammed on a dead token, and a sentence asking for patience offers no control to audit. The missing input was not a server code this time but a DEVICE-GLOBAL STATE the renderer was never given: `signOutCard` had `pending` (the queue is stuck) and not `session` (why), and the two whys have opposite instructions. Required field, never optional-with-a-default — that turned 8 call sites into compile errors, which is how the sweep was known complete; and the sheet's `onAction` needed an exhaustive switch in the same change, because a new `sign_in` member compiled clean into the sign-out path, where the gate refuses it. Worst of all and the part that generalises: THE EXIT WAS TWO CENTIMETRES UP THE SAME SCREEN, working — ask of any refusal whether the thing that resolves it is already visible elsewhere in the app. Proven by the PAIRING (S9 drives a 401 and an outage to the same measured count and asserts the sheets differ), not by either assertion alone.
- a-check-that-never-went-red-was-never-observed.md — applies to every assertion, guard and detector, hardest to the instrument you are about to cite as evidence: a negative check needs a POSITIVE CONTROL over a known-true case in the same run, or its green carries no information. Four mechanisms. The needle is empty — `startswith(b'')` is true for every input that ever existed, and `grep -c $'\r'` expands to an empty pattern matching every line, so the count equals the file's line count. The failing state is unreachable from the inputs supplied — `proveSignOut` S1 passes `pending: 3` with `engine: null`, proving the gate refuses a NUMBER, never that the number is unclearable. Or the break never reaches the assertion: eight mutations were all TS2322 compile errors, so the build stopped and no cell was observed at all. Build needles numerically, never from escapes a shell or editor may rewrite. And a control on one assertion says nothing about its neighbour.
- two-green-proofs-do-not-cover-the-seam.md — applies to any behaviour passing through more than one proven component, and to every claim of the form "X is proven and Y is proven": two separately proven components are not a proven composition, and the next defect is at the seam because no proof file owns it. `proveSync` case 11 covers a 401 mid-queue, green; `proveSignOut` S1 covers the pending gate, green; `grep signOut proveSync.ts` and `grep 401 proveSignOut.ts` both return ZERO. Neither proof is wrong. The defect exists only in the composition — a queue that cannot drain behind a dead token, under a sheet telling the operator to wait for what cannot arrive. Grep each proof for the other's vocabulary in BOTH directions; zero both ways is an unproven seam, and a two-second measurement. Then drive both sides in ONE run and assert NEGATIVELY on the rendered composition. THE REMEDY WAS THEN EXECUTED AND PAID OUT: `proveSignOut.ts` S9 is the seam test this file prescribed, and it found the sheet defect both green proofs could not see.
